## Files

| File | Why |
|---|---|
| `src/application/save/envelope.ts` | Save envelope v1: `schemaVersion`, `storageRevision`, `contentVersion`, the active run (session id, move revision, board, tray, score, status, gameplay hash, generator seed/state, next instance id), best score per gameplay hash, and settings (kept as stored; T19 defines the keys). `parseEnvelope` validates the whole record strictly. `checkRun` refuses another gameplay hash (incompatible), a mismatched board/tray, unknown shapes, inconsistent instance ids and any full line (half-resolved), and recomputes game over. `snapshot` only ever raises the best score. Pure |
| `src/application/save/save-queue.ts` | `SaveQueue` over a `SaveStore` interface: ordered writes, at most one pending snapshot (the latest), `storageRevision = expected + 1` per write. Statuses: `saving`; `saved` only after the write resolves with nothing queued; `session_only` on failure or no storage (the run stays playable; `retry()` writes the latest snapshot); `conflict` stops the writer for good. `stop()` ignores late completions. Pure, no timers |
| `src/adapters/indexeddb/save-store.ts` | Database `line-garden` v1, store `saves`, keys `current` / `backup` / `preserved`. `replace()` is one readwrite transaction: read `current`, abort with `SaveConflictError` if its `storageRevision` differs from `expected`, move the old `current` to `backup` (or to `preserved` when it was not a known-good record), write the new `current`. Resolves on `complete` only; a synchronous `put()` failure (e.g. `QuotaExceededError`) aborts with nothing written. Reports blocked opens and closes on `versionchange` |
| `src/bootstrap/saves.ts` | Startup decisions:<br>• A compatible active run resumes automatically (`?seed=` always starts new).<br>• Damaged or other-rules records ask "Restore backup" (when readable and compatible) or "Start a new game"; the old record goes to `preserved`.<br>• No IndexedDB: "Not saved (this session only)" plus Retry.<br>• Conflict: "Load latest".<br>• Blocked upgrade or a newer tab: Reload.<br>All in an HTML alert, with a one-line note that saves are browser-local |
| `src/bootstrap/main.ts` | Each accepted move is queued for saving right after it is shown. A conflict locks input (`inert`, commands refused, Resume disabled) but keeps the board rendered. Load latest reloads from storage even under `?seed=`. Teardown closes the queue and the database |
| `index.html`, `src/bootstrap/shell.css` | Save status next to the score, Retry saving button, notice region |
| `tests/persistence/save.test.ts`, `tests/browser/persistence.spec.ts` | Acceptance tests |

Browser tests use real IndexedDB in Chromium (`root` and `nested`); each test has a fresh context, so storage starts empty:
- **Restore:** 5 recorded seed-2026 moves, then a reload without a seed:
  - the canvas screenshot is byte-identical and the score and session id match;
  - the next 3 recorded moves score exactly as in Node, so the generator state was restored;
  - stored `storageRevision` 6 = the new run plus 5 moves, with `backup` at 5.
- **Saved only after completion:** an init script keeps readwrite transactions open until released. The status reads "Saving…" while held and "Saved" only after release, with the new score in storage.
- **Aborted write (quota):** `put()` throws `QuotaExceededError`:
  - the status is "Not saved (this session only)" with Retry, and play continues;
  - the stored records are byte-for-byte unchanged;
  - Retry writes only the latest state (revision +1) (`docs/evidence/t17/session-only-*.png`).
- **No IndexedDB:** the game plays, marked session only; Retry stays session only.
- **Two tabs (two pages, one context):**
  - A stale tab's move is refused. It shows the alert and "changed in another tab", its board is inert, and storage is unchanged (`conflict-*.png`).
  - Load latest shows the other tab's score and saves again. Then the first tab is stale and refused in turn.
  - Simultaneous moves: exactly one tab ends "Saved" and the other "changed in another tab"; revision +1 only.
  - A restart (`?seed=99`) in another tab stops this tab's writer, and storage keeps the new run.
- **Damaged record:**
  - Unreadable: the alert offers Restore backup; the backup's run resumes, the bad record is in `preserved` and `backup` is unchanged (`damaged-*.png`).
  - Different rules: the alert offers both choices; Start a new game gives score 0 and Saved, with the old record in `preserved`.
- **Blocked upgrade:** with another page holding a raw v1 connection, a page simulating a newer build (open at v2) shows "waiting for another Line Garden tab" and Reload. When the connection closes, it starts normally. The running old app closed its connection on `versionchange`, says a newer version opened, and is session only.
- **Node:** an envelope round-trip keeps future deals identical; best per ruleset; rejection of bad schema, keys, fractional scores, generators and cell counts; run checks; and the queue's ordering, coalescing, failure/retry, conflict stop, late attach and stop.

## Decisions

- `backup` only ever receives a record this tab treated as good. Damaged or other-rules records go to `preserved` (one slot; a later preservation replaces it).
- With `?seed=` (tests), a damaged record is preserved and replaced without asking.
- The recovery notice shows the validator's reason (e.g. "contentVersion is required"); T19 owns friendlier recovery screens.
- A conflict locks input but keeps rendering, so the board stays visible under the notice.
